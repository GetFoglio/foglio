# Excel function coverage of IronCalc 0.9.1 (Foglio)

Generated by `bench/` — re-run with:

```sh
cd bench
cargo run --release --bin functions            # one line per case
cargo run --release --bin functions -- --md    # the tables below
cargo run --release --bin functions -- --locale   # language / locale probe
cargo run --release --bin functions -- --probe '=TEXT(1,"0.0")'   # ad-hoc formulas
```

Each case is evaluated in a fresh `Model::new_empty("t","en","UTC","en")` with a small
fixture (text/number mix, an empty cell, a text "5", TRUE, errors, a sorted lookup
table, a database range — see the comment at the top of `bench/src/bin/functions.rs`),
formula in J10. Expected values are Excel's documented results (Microsoft docs examples
for the financial/statistical functions). A function is **OK** only if all of its cases
match, **MISSING** if it returns `#NAME?`, otherwise **WRONG**.

## Summary

| | Functions |
|---|---|
| Tested | 195 (list order ≈ real-world usage frequency) |
| **OK** | **179** |
| **WRONG** | **13** (AND, TEXT, LEN, CONCATENATE, YEAR, MONTH, DAY, SORT, TEXTBEFORE, TEXTAFTER, TAKE, POWER, TREND) |
| **MISSING** | **3** (AGGREGATE, GROUPBY, PIVOTBY) |
| Cases | 461 / 481 pass |

Overall the engine is in very good shape: all the "big" functions (SUM…SUMIFS, VLOOKUP /
XLOOKUP / INDEX / MATCH with wildcards and approximate match, date arithmetic incl. the
1900 leap-year bug, WORKDAY/NETWORKDAYS(.INTL), financial and statistics functions,
dynamic arrays, LET/LAMBDA/MAP/REDUCE, database functions) match Excel on every edge
case tested. The defects cluster in five root causes.

## WRONG / MISSING, by importance

### 1. Number → text conversion uses 17 significant digits instead of 15 (high impact)
Affects `&`, CONCATENATE, CONCAT, TEXTJOIN, LEN, LEFT/RIGHT/MID on numbers, … — i.e.
every formula that turns a computed number into text. Very visible to users
(`="Total: "&A1` shows `0.30000000000000004`).

| Formula | Excel | IronCalc |
|---|---|---|
| `=0.1+0.2&""` | `0.3` | `0.30000000000000004` |
| `=CONCATENATE(1/3)` | `0.333333333333333` | `0.3333333333333333` |
| `=LEN(1/3)` | 17 | 18 |
| `=1E+20&""` | `1E+20` | `100000000000000000000` |

Root cause: `ironcalc_base/src/cast.rs`, `Model::cast_to_string` does
`CalcResult::Number(f) => Ok(format!("{f}"))` (there is even a `FIXME` saying it should
use 15 digits). Fix: use `number_format::to_excel_precision_str(f)` (already exists, used
by `cell.rs`), plus Excel's switch to scientific notation for |x| ≥ 1e21 / very small x.

### 2. Omitted optional arguments (`,,`) treated as 0 / error (high impact for modern functions)
| Formula | Excel | IronCalc |
|---|---|---|
| `=SORT(A1:A3,,-1)` (the usual way to sort descending) | sorted desc | `#VALUE!` |
| `=TEXTAFTER("aXb","x",,1)` | `b` | `#VALUE!` |
| `=TEXTBEFORE("a-B","b",,1)` | `a-` | `#VALUE!` |
| `=TAKE(C1:C6,,1)` (first column) | column | `#CALC!` |

`SORT(range,1,-1)`, `TEXTAFTER(…,1,1)` work, so only `CalcResult::EmptyArg` handling of
those arguments is missing (`functions/spill_functions.rs` for SORT/TAKE,
`functions/text/common.rs` for TEXTBEFORE/TEXTAFTER). Other functions tested with
omitted args (XLOOKUP, VLOOKUP, IF, ROUND, INDEX, MATCH, SEQUENCE, TEXTSPLIT,
WORKDAY.INTL, NETWORKDAYS.INTL, PMT, TEXTJOIN, DROP) are fine.

### 3. TEXT format codes (high impact, partial)
All common codes pass: `0.00`, `#,##0`, `0%`, `0.0%`, `dd/mm/yyyy`, `yyyy-mm-dd`,
`mmm d, yyyy`, `dddd`, `mmmm`, `hh:mm`, `h:mm AM/PM`, `[h]:mm`, `000`, `$#,##0.00`,
`#,##0,` (thousands scaling), 3-section formats with literal text, `@`.
Failures:

| Formula | Excel | IronCalc |
|---|---|---|
| `=TEXT(1.5,"0.0E+00")` | `1.5E+00` | `1.5E-00` (sign of a zero exponent) |
| `=TEXT(0.75,"# ?/?")` | ` 3/4` | `  /1` (fractions not supported) |

Also in Italian (see below) `=TESTO(1234,5;"#.##0,00")` gives `1.234,5000` instead of
`1.234,50`: the format string is not de-localized before formatting.

### 4. Serial 0 rejected by YEAR / MONTH / DAY (medium: shows up as `#NUM!` for blank date cells)
| Formula | Excel | IronCalc |
|---|---|---|
| `=YEAR(0)` | 1900 | `#NUM!` |
| `=MONTH(0)` | 1 | `#NUM!` |
| `=DAY(0)` | 0 | `#NUM!` |

Common in practice: `=YEAR(B2)` on an empty B2 gives 1900 in Excel but `#NUM!` here.

### 5. AGGREGATE missing (medium)
`=AGGREGATE(9,6,range)` (sum ignoring errors) is a popular idiom. Not in the function
table at all (`#NAME?`). Could be implemented on top of the existing SUBTOTAL code
(`functions/subtotal.rs`) plus the LARGE/SMALL/PERCENTILE/QUARTILE array forms (14–19).

### 6. AND with a text argument (low)
`=AND(TRUE,"a")` → Excel `#VALUE!`, IronCalc `TRUE` (text literal ignored instead of
rejected; text inside ranges is correctly ignored).

### 7. POWER of a negative base with fractional exponent (low)
`=POWER(-8,1/3)` → Excel `#NUM!`, IronCalc `-2` (LibreOffice behaviour).

### 8. TREND with array-constant inputs (low)
`=TREND({1,2,3},{1,2,3},4)` → `#REF!`; with ranges (`=TREND(C1:C3,C1:C3,4)`) it is
correct. Array arguments are not accepted.

### 9. GROUPBY / PIVOTBY missing (low today, rising)
New Excel 365 functions, `#NAME?`.

## Other behaviours checked and found correct
Text/number coercion (`"1"+1`, `TRUE+1`, `"2024-01-15"+0`, `10>"9"` is FALSE, empty cell
as 0 / ""), case-insensitive comparisons, `-2^2 = 4`, `0.1+0.2=0.3` is TRUE (15-digit
compare), ROUND half away from zero incl. `ROUND(2.675,2)=2.68`, `ROUND(-1.005,2)`,
INT/MOD/CEILING/FLOOR sign rules, wildcards `*`, `?`, `~` in SUMIF/COUNTIF/MATCH/
VLOOKUP/XLOOKUP/SEARCH, COUNTBLANK counting `=""`, `DATE(1900,3,1)=61`, `DATE(24,1,1)`
→ 1924, month/day overflow, EDATE/EOMONTH end-of-month clamping, WEEKNUM 53,
ISOWEEKNUM, DATEDIF Y/M/D/YM, DATEVALUE in ISO / US / `15-Jan-2024` forms, whole
column references (`SUM(C:C)`).

Not verified (Excel behaviour uncertain, left out of the score): `COUNTIF(range,"5")`
against a text "5" (IronCalc counts it), lenient `DATEVALUE("15/01/2024")` in an en-US
locale (IronCalc accepts it, Excel en-US returns `#VALUE!`), DATEDIF "MD".

## Language and locale support

* **Languages** (function names, booleans, error names): `en`, `it`, `de`, `es`, `fr`
  (from `ironcalc_base/src/language/language.bin`; ids are the bare two-letter codes,
  `it-IT`/`en-US` are rejected).
* **Locales** (`ironcalc_base::get_supported_locales()`): `de`, `en`, `en-GB`, `es`,
  `fr`, `it`. Again bare ids; there is no `en-US` (that is `en`) and no `it-IT`.
* `Model::new_empty("t","it","Europe/Rome","it")` works and behaves like Italian Excel:

| Input | Result |
|---|---|
| `1,5` / `1.234,5` / `15/01/2024` | parsed as 1.5 / 1234.5 / date 45306 |
| `=SOMMA(A1;A3)`, `=SE(A3>1;"sì";"no")`, `=CERCA.VERT(2;A3:A3;1;FALSO)`, `=SE.ERRORE(1/0;"x")`, `=CONTA.SE(A1:A3;">1")`, `=ARROTONDA(2,5;0)`, `=MEDIA(…)`, `=OGGI()`, `=VERO` | all evaluate correctly; `;` is the argument separator and `,` the decimal separator inside formulas (`=1,5+1` → 2,5) |
| `=SUM(A1,A3)` (English name) | `#ERRORE!` — the parser only accepts the active language |
| display | `1234.5` with `#,##0.00` → `1.234,50`; `=OGGI()` → `09/11/2026`; errors `#ERRORE!`, booleans `VERO/FALSO`; default sheet name `Foglio1` |
| `get_localized_cell_content` | returns the formula in Italian (`=SOMMA(A1;A3)`) |

Caveat: `TESTO()`/`TEXT()` format codes must currently be written with English
separators (`"#,##0.00"`); Italian-style codes are mis-rendered (see §3). Formulas are
stored language-neutrally, so a workbook can be switched with `set_language("it")` /
`set_locale("it")` at runtime.
